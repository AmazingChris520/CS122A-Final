# FPGA Tetris Controller Project

This project runs a simple Tetris-style game on the iCESugar Pro FPGA and uses a Raspberry Pi Pico as the input controller. The Pico reads the joystick and push buttons, converts the player input into a small command byte, and sends that command to the FPGA over SPI. The FPGA handles the game logic and renders the playfield to the display.

## System Overview

The project is split into two main parts:

1. **Raspberry Pi Pico**
   - Reads the joystick and button inputs.
   - Converts each input into an 8-bit control command.
   - Sends the command byte to the FPGA using SPI.

2. **iCESugar Pro FPGA**
   - Receives the control byte from the Pico.
   - Updates the active Tetris piece.
   - Handles gravity, movement, rotation, locking, row clearing, and spawning.
   - Generates the video output for the 10 by 20 playfield.

Basic data flow:

```text
Joystick / Buttons -> Raspberry Pi Pico -> SPI -> iCESugar Pro FPGA -> Display
```

## Raspberry Pi Pico Connections

The Pico is used as the controller board. It reads the physical inputs and sends the command byte to the FPGA.

### Input Connections

| Pico Pin | Connected Device | Purpose |
|---|---|---|
| GP26 / ADC0 | Joystick X-axis | Reads left and right movement |
| GP15 | Joystick push button | Extra joystick button input |
| GP12 | Left push button | Fast drop command |
| GP13 | Right push button | Rotate command |
| GND | Button and joystick ground | Common ground reference |
| 3V3 or VSYS | Joystick VCC, depending on module | Powers the joystick module |

For the push buttons, one side of the button goes to the Pico GPIO pin and the other side goes to ground. The Pico firmware should use internal pull-ups so the button reads high when idle and low when pressed.

Most 4-pin push buttons have two pins connected together on each side. Use one pin from each side of the button. Do not use two pins from the same side, because that will not create a switching connection.

### SPI Connections from Pico

| Pico Pin | SPI Signal | Purpose |
|---|---|---|
| GP17 | CS / CSN | Selects the FPGA SPI receiver |
| GP18 | SCK | SPI clock |
| GP19 | MOSI / TX | Sends the control byte to the FPGA |
| GND | Ground | Shared reference with FPGA |

The Pico is the SPI master. The FPGA is the SPI receiver. Only MOSI is needed because the FPGA does not need to send data back to the Pico for the current version of the project.

## iCESugar Pro Connections

The iCESugar Pro receives the SPI command byte and uses it to control the Tetris game.

| iCESugar Pro Pin | Connected Pico Pin | Signal |
|---|---|---|
| P13 | GP17 | CS / CSN |
| P14 | GP18 | SCK |
| M13 | GP19 | MOSI / TX |
| GND | Pico GND | Common ground |

The FPGA logic runs from the board clock and uses the incoming control byte to update the game state. The video output is generated by the FPGA and sent to the connected display through the board's video output hardware.

## Control Byte Encoding

The Pico sends an 8-bit value to the FPGA. The `tetris_display` module uses this value to decide what action to perform.

| Control Byte | Action |
|---|---|
| `8'd1` | Move piece right |
| `8'd2` | Move piece left |
| `8'd3` | Rotate piece clockwise |
| `8'd4` | Fast drop while held |
| Other value | No movement |

The FPGA does not directly read the joystick or buttons. It only responds to the command byte that the Pico sends.

## FPGA Game Logic

The main FPGA game module is `tetris_display`. It builds a 10 column by 20 row playfield and stores locked blocks in a board array.

```systemverilog
logic [FIELD_COLS-1:0] board [FIELD_ROWS-1:0];
```

Each bit in the board represents one locked cell:

```text
board[row][col] = 1 -> locked block exists at that cell
board[row][col] = 0 -> empty cell
```

The active piece is tracked separately from the locked board using:

| Signal | Purpose |
|---|---|
| `piece_type` | Current tetromino type |
| `piece_rot` | Current rotation state |
| `piece_row` | Top-left row of the 4 by 4 piece box |
| `piece_col` | Top-left column of the 4 by 4 piece box |

The active piece is not written into the board until it locks.

## Tetrominoes

The code supports all seven standard tetrominoes:

| Name | Code |
|---|---|
| I | `P_I` |
| O | `P_O` |
| T | `P_T` |
| S | `P_S` |
| Z | `P_Z` |
| J | `P_J` |
| L | `P_L` |

Each piece is represented inside a 4 by 4 local box. The `piece_cell()` function checks whether a local row and column inside that box is occupied for the current piece type and rotation.

## Piece Placement and Collision

Before the FPGA moves or rotates a piece, it checks whether the new position is valid.

The `piece_valid()` function checks that:

- Every occupied cell stays inside the 10 by 20 board.
- The active piece does not overlap any locked cell.
- The move, fall, or rotation is legal before it is applied.

This same check is used for left movement, right movement, falling, and rotation.

## Game State Machine

The game uses four main states.

| State | Purpose |
|---|---|
| `S_SPAWN` | Creates a new active piece at the top of the board |
| `S_FALLING` | Lets the active piece move, rotate, and fall downward |
| `S_LOCKING` | Gives the piece a short delay after it lands |
| `S_CLEAR` | Checks for full rows and clears them |

### Spawn State

A new piece starts near the top center of the board. The piece type is chosen using an 8-bit LFSR.

### Falling State

While falling, the piece can:

- Move left.
- Move right.
- Rotate clockwise.
- Drop normally due to gravity.
- Fast drop when the fast drop command is held.

Normal gravity moves the piece down once per second using the 25 MHz clock.

### Locking State

When the active piece reaches the bottom of the board or lands on top of another locked block, the game enters the locking state.

During the lock delay, the player can still move or rotate the piece. After the delay expires, the occupied cells of the active piece are written into the board array as locked cells.

### Clear State

After a piece locks, the FPGA scans the board from the bottom row upward. If a row is full, that row is removed and all rows above it shift down by one.

After row clearing is complete, the game returns to the spawn state.

## Timing

The timing values assume a 25 MHz FPGA clock.

| Signal | Value | Meaning |
|---|---:|---|
| `FALL_TICKS` | 25,000,000 | Normal fall every 1.0 second |
| `MOVE_TICKS` | 3,750,000 | Movement and rotation repeat every 150 ms |
| `FAST_DROP_TICKS` | 1,250,000 | Fast drop step every 50 ms |
| `LOCK_TICKS` | 12,500,000 | Lock delay of 0.5 seconds |

## Random Piece Selection

The FPGA uses an 8-bit LFSR to generate pseudo-random piece selection. The LFSR runs continuously while the game is active.

The lower 3 bits of the LFSR are mapped to the seven pieces. Since 3 bits can represent 8 values, the extra value maps to the T piece.

This is pseudo-random selection, not a 7-bag system.

## Display Logic

The playfield is 10 columns by 20 rows. Each cell is 16 pixels wide and 20 pixels tall. The playfield is centered inside a 640 by 480 video frame.

| Display Item | Color |
|---|---|
| Active piece | Red |
| Locked blocks | Grey |
| Playfield background | Dark green |
| Grid lines | Green |
| Border | Bright green |
| Outside screen area | Black |

The display logic maps the current VGA pixel location to a playfield row and column. It then checks whether that cell belongs to the active piece, a locked block, the grid, or the border.

## Current Project Status

The current design supports:

- A 10 by 20 Tetris playfield.
- All seven tetrominoes.
- Left and right movement.
- Clockwise rotation.
- Fast drop.
- Gravity based falling.
- Lock delay after landing.
- Locked block rendering.
- Full row clearing.
- Pseudo-random piece spawning.
- Pico to FPGA control over SPI.

The FPGA game logic is driven by the `control` byte. Any new input added on the Pico side should be mapped to a new command value before the FPGA can use it.
